# iMessage on Linux without a relay — research findings (2026-10-09)

## The one-sentence answer

A Linux machine can talk to Apple's iMessage servers directly (no Mac/iPhone
relay, no third-party server holding your login), **but Apple's registration
step requires a cryptographic proof minted from a *real* Mac's hardware
identity.** Those identifiers must be extracted from a Mac **once** (a few
minutes, no software install beyond running a script). After that the Mac can
be turned off, wiped, or sold; it is never contacted again. There is no known
way to fabricate them since Apple's December 2023 crackdown on Beeper Mini.

## How iMessage actually works (as reverse engineered)

| Layer | What it is | Open implementation |
|---|---|---|
| **Albert activation** | `albert.apple.com` issues a device push certificate to a "device" that presents a FairPlay device cert chain. Any x86 box can do this with a legacy cert. | pypush `albert.py`, rustpush `activation.rs` (uses `certs/legacy-fairplay`) |
| **APNs courier** | Persistent TLS to `N-courier.push.apple.com:5223`. Client cert at app layer. Topics (`com.apple.madrid` = iMessage). Bidirectional; also carries IDS pseudo-HTTP queries. | pypush `apns.py`, rustpush `aps.rs` |
| **GSA / Apple ID login** | SRP-6a login to `gsa.apple.com` with 2FA. Needs **anisette** (device-attestation headers `X-Apple-I-MD*`). | `icloud-auth` + `omnisette` (MPL-2.0) |
| **Anisette** | Generated by Apple's ADI library. Options on Linux: (a) remote anisette-v3 server (default `https://ani.sidestore.io`), (b) on-device via Apple Music Android `libstoreservicescore` loaded with an ELF loader (upstream deleted this; the `relay` project restores it), (c) OpenBubbles ClearADI — **closed source**. | omnisette `remote_anisette_v3.rs` |
| **IDS registration** | Upload encryption/signing public keys + device capabilities for each handle (email). Requires **validation data**. | rustpush `ids/` |
| **Validation data (NAC)** | A signed blob (517 bytes for the Intel reference identity, 389 for a real Apple Silicon Mac; the size depends on the identity) produced by Apple's obfuscated `IMDAppleServices` (x86-64 Mach-O). The only working approach: run that binary under the **Unicorn** CPU emulator, stubbing ~37 CoreFoundation/IOKit calls so it "sees" a real Mac's identity. Apple checks that the identity is a real, un-blocked Mac. | pypush `emulated/{nac,jelly}.py` (SSPL); Rust port in `dennisshey/relay` patch `03-open-absinthe.patch` (copied to `docs/reference-relay-03-open-absinthe.patch`). OpenBubbles' `open-absinthe` is now **closed** (`OpenAbsinthe-Stub` = three `todo!()`s). |
| **Key lookup + message crypto** | IDS lookup returns peers' public keys + push tokens. Messages: `pair-ec` (ECDH + AES-CTR + ECDSA; HMAC-tagged AES key). PQ3 is additive and not required to interoperate. | rustpush `imessage/` |
| **Attachments** | MMCS (iCloud blob store) upload/download with chunked encryption. | rustpush `icloud/mmcs.rs` |
| **Renewal** | Registration must be renewed periodically; with Mac-class identity it renews indefinitely with **no** connection to the Mac. | rustpush |

### Mac hardware identity: the 14 fields

From OpenBubbles `Mac-Hardware-Info` (Swift, IOKit) and pypush `data.plist`:

| Field | Source on the Mac |
|---|---|
| `product_name` | `IODeviceTree:/` `product-name` (or `model`) e.g. `Macmini7,1` |
| `io_mac_address` | primary `IOEthernetInterface` parent `IOMACAddress` |
| `platform_serial_number` | `IOPlatformSerialNumber` |
| `platform_uuid` | `IOPlatformUUID` |
| `root_disk_uuid` | `IODeviceTree:/chosen` `boot-uuid` |
| `board_id` | `IODeviceTree:/` `board-id` (Intel) or `Mac-`+hex(`chosen/board-id`) (Apple Silicon) |
| `os_build_num` | `sysctl kern.osversion` |
| `rom` | `IODeviceTree:/options` `4D1EDE05-…:ROM` (Intel) or sha256(`chosen/unique-chip-id`)[-6:] (Apple Silicon) |
| `mlb` | `options` `4D1EDE05-…:MLB` or `mlb-serial-number` |
| `platform_serial_number_enc` | `IOPower:/` property `Gq3489ugfi` (FairPlay-encrypted) |
| `platform_uuid_enc` | `IOPower:/` `Fyp98tpgj` |
| `root_disk_uuid_enc` | `IOPower:/` `kbjfrfpoJU` |
| `rom_enc` | `IOPower:/` `oycqAZloTNDm` |
| `mlb_enc` | `IOPower:/` `abKPld1EcMni` |

All of these are readable with `ioreg`/`sysctl`/`nvram` from a normal user
account on macOS; no Xcode needed. A missing field makes the blob silently
shrink (517 → 389 bytes for the reference identity) and Apple refuses with
error 6001. A 389-byte blob is not by itself a failure, though: a complete
Apple Silicon identity also yields 389 bytes, and Apple accepted
it for registration on 2026-10-16.

## What Apple has blocked, and the residual risks

* Dec 2023: Beeper Mini's fabricated/shared Mac serials were blocked within
  days; Apple now scores the hardware identity (real serial, model match,
  account age). **Use your own Mac's identity, for your own account.**
* Macs whose identity was shared with *many* users (Beeper's "relay" phase)
  were banned from iMessage. OpenBubbles' FAQ: sharing with >20 users or for
  spam → device block (temporary 1–2 days, or permanent; Apple support calls
  have reversed permanent ones). Single-user use is not reported to cause bans.
* A Mac-class identity registers the account's **email handles** and the
  **phone number an iPhone on the account has linked** (Apple offers it in
  `id-get-handles` and accepted it for registration on 2026-10-17; the
  relay project's patch had assumed status 6001 for any `tel:` handle, so
  the daemon falls back to emails alone if that happens). A number *without*
  such an iPhone needs iPhone-class validation data, which is out of scope.
* Apple can force re-registration at any time; the daemon must handle it
  automatically (it can, since the emulator runs locally).
* Apple **Contact Key Verification** must be off on the account (third-party
  devices can't participate).
* Apple ToS: you are using Apple's service from an unapproved client. Account
  suspension is the realistic worst case. Don't send bulk messages.

## Decision: reuse rustpush as the protocol engine; write everything else

Reimplementing APNs/IDS/pair-ec/MMCS/group chats/tapbacks from scratch is a
multi-month effort with high breakage risk, and the result would still be
SSPL-adjacent work. rustpush is actively maintained and already interoperates
with current iOS/macOS. The pieces that are *missing* for a self-contained
Linux client are exactly the pieces we build:

1. **NAC emulator crate** (replacing the closed `open-absinthe`).
2. **Mac identity extraction script** (run once on the Mac).
3. **Anisette** via remote v3 (default), with local ADI as a later option.
4. **Daemon + D-Bus API + local store**, **CLI**, **KDE/Kirigami app**.

Consequence: the project is licensed **SSPL-1.0** (rustpush's license applies
to derived works). Fine for personal use and for publishing source.

## Update 2026-10-16: remote anisette rejected (-80045)

Since about 2026-10-13 `gsa.apple.com` rejects SRP `init` requests whose
anisette headers come from `anisette-v3-server` (every public server; it
runs Apple's *Android* CoreADI) when `X-Mme-Client-Info` claims a Mac:
status -80045 "This action cannot be completed at this time." Confirmed
across SideStore, AltStore, iLoader and FindMy.py users; headers from a
real Mac's `AOSKit` (`retrieveOTPHeadersForDSID:@"-2"`) keep working.
Our fix: `anisette_command` runs `tools/mac-anisette/imessage-anisette`
on the user's Mac over ssh (same AOSKit/AuthKit calls as omnisette's
`aos_kit.rs`). Sources: Dadoum/anisette-v3-server#61, SideStore#1658,
AltStore#1828, iloader#859.

## Update 2026-10-17: transcript backgrounds

Messages "Backgrounds" (iOS/macOS 26) are synced per chat with a
`SetTranscriptBackground` message (`c` = 138; rustpush
`SetTranscriptBackgroundMessage`): `Set { traba (aid, 1), tbid (sequence
number), cid?, traboid (MMCS object), trabapv (payload version, 1),
trabaid (background UUID), trabar (MMCS URL), trabas (signature), trabak
(key, one leading byte + 32-byte file key), trabafs (size) }` or
`Remove { traba, tbid, cid?, trababr: true }`. The payload is an ordinary
MMCS file, so the attachment download path handles it (the daemon wraps
`to_mmcs()` in an attachment locator).

No live `SetTranscriptBackground` arrived while we listened (25 min after
asking for a re-set), so the format below comes from a macOS 26.6.2 Mac
that has the chats' backgrounds:

* `chat.db` → `chat.properties` (binary plist) carries the same fields under
  `backgroundProperties`: `trabaid`, `trabapv` (1), `trabafs`, `traboid`,
  `trabar`, `trabas`, `trabak`, plus `trabav` (a large version number) and
  `trabaCommSafety` (0); `backgroundChannelGUID` sits at the top level. The
  key material is there in the clear, so treat `chat.db` as secret.
* `~/Library/Messages/TranscriptBackgroundCache/<trabaid>` is the payload: a
  PosterKit configuration, either an **uncompressed Apple Archive**
  (`AA01` headers; fields `TYP1`, `PATP`, `MOD2`, `FLG1`, `CTMT`, `MTMT`,
  `DATB` + data) or a **stored zip** (`manifest.plist`,
  `configuration/com.apple.posterkit.*`). For a Photos poster it holds
  `configuration/versions/0/contents/<uuid>/output.layerStack/`
  `portrait-layer_background.HEIC` (the picture, ~0.3-0.5 MB) next to
  `Contents.json` (layer frames), `ConfigurationModel.plist`,
  `com.apple.posterkit.provider.instance.{rendering,titleStyle}Configuration.plist`
  and `manifest.plist`. The cached file is smaller than `trabafs`, so the
  Mac may re-pack what it downloaded; whether the MMCS payload itself is
  the same AA/zip container is unconfirmed until a live capture.
* `<trabaid>-watchBackground` is a binary plist `{backgroundImageData (PNG),
  extensionIdentifier ("com.apple.PhotosUIPrivate.PhotosPosterProvider"),
  isHighKey, luminance}`: a pre-rendered picture.

The daemon (`crates/imessaged/src/background.rs`) takes the
`*layer_background*` image out of either container (or the PNG out of a
watch plist, or a plain image as is) and exposes it as the chat's
`background.path`; Qt shows HEIC through kimageformats (`kimg_heif`).
Non-photo posters (colour, gradient, emoji) have not been seen yet; they
would come out with `path: null`.

Seen 2026-10-17 with `imsg import-mac --backgrounds` (10 chats with a
background on one Mac): the zip posters are not always stored. One Photos
poster (2.3 MB) is a **deflate-compressed** zip (method 8 for every entry,
`portrait-layer_background.HEIC` included, plus `input.segmentation/`
with `proxy.heic` and `Adjusted.JPG`), which the daemon's stored-zip
reader does not open; another (6 KB) has only plists and no
`contents/<uuid>/` directory at all (a non-photo poster). Both have a
`-watchBackground` sibling whose PNG the daemon reads, so the importer
falls back to it when the poster yields no picture.

Sending: rustpush can build the message
(`SetTranscriptBackgroundMessage::from_mmcs(MMCSFile::new(..))`), but the
payload has to be a PosterKit archive that iPhones accept; we have not
captured an outgoing one or verified what a minimal archive must contain,
so sending is not implemented.
